EKS · IAM · CROSSPLANE

Centralized IRSA across AWS accounts

Replace long-lived access keys with temporary credentials for centrally hosted Crossplane providers. One control plane can manage messaging infrastructure across multiple AWS accounts.

Illustrative implementation using example account IDs. Assumes Crossplane v2 namespaced AWS managed resources and an Upbound AWS provider that supports IRSA and assumeRoleChain. Verify the installed schemas before applying.

1. Architecture

Central EKS cluster
SQS provider + SNS provider
↓ shared DeploymentRuntimeConfig
Kubernetes ServiceAccount
crossplane-aws · annotated with IAM role ARN
↓ signed token → STS AssumeRoleWithWebIdentity
Source IAM role · 111111111111
crossplane-provider-aws
↓ STS AssumeRole · selected by ClusterProviderConfig
Dev · 222222222222
Messaging IAM role → SQS/SNS
QA · 333333333333
Messaging IAM role → SQS/SNS

Why this is powerful

Only the cluster running the providers needs IRSA for this provisioning flow. Target accounts need IAM roles, not another Crossplane installation or OIDC provider. Application pods in target clusters may still need their own identity for sending or consuming messages.

Before

Provider → Kubernetes Secret → IAM user → target role → AWS API

After

Provider → ServiceAccount token → source role → target role → AWS API

2. How IRSA works

The EKS control plane signs a short-lived ServiceAccount token. The OIDC issuer publishes public keys that AWS can use to verify the signature. The IAM OIDC provider establishes which issuer AWS trusts. The trust policy limits which ServiceAccount may assume the role. A permission policy determines what the assumed role may do.

  1. The IRSA webhook injects the role ARN and projected token path into a new pod using the annotated ServiceAccount.
  2. The AWS SDK exchanges the token through STS AssumeRoleWithWebIdentity.
  3. STS validates issuer, signature, expiration, audience and role trust, then returns temporary credentials.
  4. The provider uses those credentials to call STS AssumeRole for the target environment role.
  5. The provider uses the target role session for SQS/SNS API calls. The SDK refreshes credentials as required.

3. Configure AWS IAM

Step 1 — Verify the source OIDC provider

aws eks describe-cluster --name central-eks --region us-west-2 \
  --query 'cluster.identity.oidc.issuer' --output text
aws iam list-open-id-connect-providers

Confirm the issuer matches a registered IAM OIDC provider in the source account, with sts.amazonaws.com as an allowed client ID. If missing, associate it using the official EKS instructions.

Step 2 — Create the source role

Create crossplane-provider-aws in account 111111111111. Replace EXAMPLEOIDC with the actual issuer ID. The trust policy grants only the specified namespace and ServiceAccount access.

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "Federated": "arn:aws:iam::111111111111:oidc-provider/oidc.eks.us-west-2.amazonaws.com/id/EXAMPLEOIDC"
    },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "oidc.eks.us-west-2.amazonaws.com/id/EXAMPLEOIDC:aud": "sts.amazonaws.com",
        "oidc.eks.us-west-2.amazonaws.com/id/EXAMPLEOIDC:sub": "system:serviceaccount:crossplane-system:crossplane-aws"
      }
    }
  }]
}

Attach the following permission policy. Start with Dev only; add QA and other approved roles after validation. Do not grant wildcard AssumeRole access.

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "sts:AssumeRole",
    "Resource": [
      "arn:aws:iam::222222222222:role/crossplane-messaging"
    ]
  }]
}

Step 3 — Configure the target role

In the Dev account, create or update a dedicated least-privilege messaging role. Add this statement to its existing trust policy; preserve existing authorized consumers during migration.

{
  "Effect": "Allow",
  "Principal": {
    "AWS": "arn:aws:iam::111111111111:role/crossplane-provider-aws"
  },
  "Action": "sts:AssumeRole"
}

The target role's permissions must cover the actual SQS/SNS resources and lifecycle actions required by the Composition, including tagging, queue policies and subscriptions. Scope resources and actions as tightly as supported. The source permission and target trust must both allow role assumption.

4. Configure Crossplane

Step 4 — Create one externally managed ServiceAccount

apiVersion: v1
kind: ServiceAccount
metadata:
  name: crossplane-aws
  namespace: crossplane-system
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::111111111111:role/crossplane-provider-aws

Step 5 — Share an existing ServiceAccount via runtime config

apiVersion: pkg.crossplane.io/v1beta1
kind: DeploymentRuntimeConfig
metadata:
  name: aws-irsa
spec:
  deploymentTemplate:
    spec:
      replicas: 1
      selector: {}
      template:
        spec:
          serviceAccountName: crossplane-aws

Use deploymentTemplate to reference the existing ServiceAccount. Do not set the same serviceAccountTemplate.metadata.name on multiple packages: ownership conflicts can occur. Preserve existing scheduling, scaling and resource settings. Shared ServiceAccounts combine Kubernetes permissions; separate identities are preferable when isolation matters.

Step 6 — Update provider references

apiVersion: pkg.crossplane.io/v1
kind: Provider
metadata:
  name: provider-aws-sqs
spec:
  package: xpkg.upbound.io/upbound/provider-aws-sqs:v2.9.0
  runtimeConfigRef:
    name: aws-irsa
---
apiVersion: pkg.crossplane.io/v1
kind: Provider
metadata:
  name: provider-aws-sns
spec:
  package: xpkg.upbound.io/upbound/provider-aws-sns:v2.9.0
  runtimeConfigRef:
    name: aws-irsa

Apply the ServiceAccount and runtime config first. Keep the installed provider package versions unchanged; the versions here are illustrative. Let the provider pods roll out. Keep functions on a separate runtime config unless they explicitly need AWS access.

5. Switch the authentication source

After verifying the pod identity, update the existing ClusterProviderConfig in place. Keep its name and target role unchanged.

Before

credentials:
  source: Secret
  secretRef:
    namespace: crossplane-system
    name: aws-creds
    key: credentials

After

credentials:
  source: IRSA
apiVersion: aws.m.upbound.io/v1beta1
kind: ClusterProviderConfig
metadata:
  name: aws-dev
spec:
  credentials:
    source: IRSA
  assumeRoleChain:
    - roleARN: arn:aws:iam::222222222222:role/crossplane-messaging

A Queue or Topic managed resource continues to reference the same configuration:

spec:
  providerConfigRef:
    name: aws-dev
    kind: ClusterProviderConfig

The Composition, XRD and XR remain unchanged when the reference and resource identities remain the same. For QA, create aws-qa with the QA role ARN and authorize that ARN in the source role. There is no need to install a provider for every account.

6. Validate before and after cutover

kubectl get providers
kubectl get pods -n crossplane-system
kubectl get sa crossplane-aws -n crossplane-system -o yaml
kubectl describe pod PROVIDER_POD -n crossplane-system
kubectl explain clusterproviderconfig.spec.credentials --api-version=aws.m.upbound.io/v1beta1

Confirm AWS_ROLE_ARN and AWS_WEB_IDENTITY_TOKEN_FILE are present. In an authorized short-lived test pod using the same ServiceAccount, run:

aws sts get-caller-identity
aws sts assume-role \
  --role-arn arn:aws:iam::222222222222:role/crossplane-messaging \
  --role-session-name irsa-test \
  --query AssumedRoleUser.Arn --output text

The first call must identify the source role; the second must return the target role ARN. Remove the test pod immediately. Verify fresh provider reconciliation, managed resource conditions and CloudTrail STS events, rather than relying on an old Ready=True condition.

kubectl get managed -A
kubectl logs -n crossplane-system PROVIDER_POD --since=10m

7. Rollback and cleanup

Use two GitOps changes: first enable IRSA on provider pods, then change the Dev ClusterProviderConfig. Keep the old Secret until the migration is proven. If authentication fails, revert the existing ProviderConfig to source: Secret and restore its secretRef, then sync and verify reconciliation. Do not delete providers, XRs or managed resources to switch credentials. Avoid Argo CD Force/Replace during this migration.

Only remove the Secret and deactivate old IAM user credentials after checking all consumers, including Terraform and other pipelines. Existing AWS resources should remain intact if the target account, region and external identities are unchanged.

8. Production controls

  • Use least-privilege target roles; avoid administrator roles and wildcard role assumption.
  • Separate production and non-production identities or control planes where required. Shared ServiceAccounts do not isolate provider privileges.
  • Restrict who can create pods with privileged ServiceAccounts and who can change ProviderConfigs or environment inputs.
  • Ensure network access to STS and required AWS APIs; restrict node metadata access.
  • Keep IAM configuration in reviewed infrastructure-as-code and monitor CloudTrail and reconciliation failures.
