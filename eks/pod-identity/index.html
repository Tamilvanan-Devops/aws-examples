EKS · IAM · TEMPORARY AWS CREDENTIALS

Amazon EKS Pod Identity

Understand how pods access S3, SQS, SNS and other AWS services without storing long-lived IAM user credentials. A step-by-step guide for DevOps and application developers.

Scope: AWS EKS application workloads. The existing Crossplane/IRSA guide is separate. All example account IDs, ARNs and images are illustrative. The repository does not run Terraform automatically.

2. Architecture for many applications

Install the Pod Identity Agent once per eligible EKS cluster. Applications share the cluster agent but should have separate, least-privilege application identities. An application that does not need AWS APIs needs no Pod Identity role.

3. Understand the four components

IdentityPurpose
EC2 worker node IAM roleAuthorizes the agent to call EKS Auth using eks-auth:AssumeRoleForPodIdentity. It should not hold broad application S3/SQS permissions.
Kubernetes service accountIdentifies the pod, e.g. orders/orders-api.
Application IAM roleSpecifies exactly which AWS actions/resources the application may access.
Pod Identity associationMaps cluster + namespace + service account to the application IAM role in EKS.

Why does the agent need the node role? The agent authenticates to the EKS Auth API with node credentials, presents the pod token, and obtains temporary credentials for the app-specific IAM role. The node's EKS Auth permission alone does not grant S3/SQS access.

Step 1 · Install Pod Identity Agent

Prerequisites: supported EKS cluster, supported Linux EC2 nodes (not EKS Fargate), AWS CLI, kubectl and IAM permissions. In AWS Console: EKS → Clusters → selected cluster → Add-ons → Get more add-ons → EKS Pod Identity Agent. Do not recreate an existing add-on.

export AWS_REGION=us-west-2
export CLUSTER=example-dev-cluster
aws eks describe-addon --cluster-name "$CLUSTER" --addon-name eks-pod-identity-agent --region "$AWS_REGION"
# Only if not already installed:
aws eks create-addon --cluster-name "$CLUSTER" --addon-name eks-pod-identity-agent --region "$AWS_REGION"
kubectl -n kube-system get daemonset eks-pod-identity-agent

Confirm the EC2 node role has eks-auth:AssumeRoleForPodIdentity; typically it is included in AmazonEKSWorkerNodePolicy. Private nodes need EKS Auth connectivity, often through interface endpoint com.amazonaws.us-west-2.eks-auth. Pods need to reach agent endpoint 169.254.170.23:80. See Terraform agent setup and variables.

Step 2 · Create an application IAM role

Example orders-api-pod-role in the EKS cluster's AWS account. IAM Console → Roles → Create role → Custom trust policy. Trust permits the EKS Pod Identity service; use request-tag conditions to restrict to the expected cluster, namespace and service account. Keep EKS Pod Identity session tags enabled.

{
 "Version":"2012-10-17",
 "Statement":[{
  "Effect":"Allow",
  "Principal":{"Service":"pods.eks.amazonaws.com"},
  "Action":["sts:AssumeRole","sts:TagSession"],
  "Condition":{"StringEquals":{
   "aws:RequestTag/eks-cluster-arn":"arn:aws:eks:us-west-2:111122223333:cluster/example-dev-cluster",
   "aws:RequestTag/kubernetes-namespace":"orders",
   "aws:RequestTag/kubernetes-service-account":"orders-api"
  }}
 }]
}

Attach a separate permissions policy for actual application AWS calls. Example: S3 object read only, not full S3 administrator access:

{
 "Version":"2012-10-17",
 "Statement":[{
  "Effect":"Allow","Action":"s3:GetObject",
  "Resource":"arn:aws:s3:::example-orders-bucket/incoming/*"
 }]
}

Trust answers who can assume the role; permissions answer what the role may do. For SQS or SNS, use exact actions and queue/topic ARNs required by the workload.

Step 3 · Create the service account

apiVersion: v1
kind: Namespace
metadata:
  name: orders
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: orders-api
  namespace: orders

Apply serviceaccount.yaml. Unlike IRSA, Pod Identity needs no eks.amazonaws.com/role-arn annotation.

Step 4 · Create the EKS association

AWS Console: EKS → your cluster → Access → Pod Identity associations → Create. Select namespace orders, service account orders-api, IAM role orders-api-pod-role.

aws eks create-pod-identity-association  --cluster-name example-dev-cluster  --namespace orders  --service-account orders-api  --role-arn arn:aws:iam::111122223333:role/orders-api-pod-role  --region us-west-2
aws eks list-pod-identity-associations --cluster-name example-dev-cluster --region us-west-2

Manage this with Terraform in real environments. Restrict who may create/update/delete associations and call iam:PassRole.

Step 5 · Update Helm/Deployment

spec:
  template:
    spec:
      serviceAccountName: orders-api
      containers:
      - name: orders-api
        image: REPLACE_WITH_REAL_IMAGE
        env:
        - name: AWS_REGION
          value: us-west-2
        - name: AWS_EC2_METADATA_DISABLED
          value: "true"

Keep your application's existing container resources, ports, probes and security settings. See deployment example. Existing pods should be restarted after association creation using kubectl -n orders rollout restart deployment/orders-api.

6. Terraform examples

Agent Terraform installs the add-on and optionally creates EKS Auth endpoint. Application Terraform creates a restricted IAM role, AWS permission policy, and EKS association. See variables, outputs, and example inputs.

cd eks/pod-identity/terraform
cp terraform.tfvars.example terraform.tfvars
# Replace examples with approved values.
terraform init
terraform fmt -check
terraform validate
terraform plan
# Apply only after review.

For many workloads, make this a reusable versioned Terraform module, invoked per app/environment. Do not create duplicate resources if an add-on or association is already managed in another Terraform state.

7. Developer-side .NET changes

Use a compatible AWS SDK and its default credential chain. Old code that passes hardcoded or environment-provided keys must be replaced.

Before

var credentials = new BasicAWSCredentials(accessKey, secretKey);
var s3 = new AmazonS3Client(credentials, RegionEndpoint.USWest2);

After

var s3 = new AmazonS3Client(RegionEndpoint.USWest2);

ASP.NET Core can use the usual dependency-injection registrations (AddDefaultAWSOptions and AddAWSService<IAmazonS3>). Verify AWSSDK.Core meets AWS SDK minimum requirements. After successful migration, remove legacy keys from code, appsettings, Kubernetes, Helm and Doppler. Keep non-secret bucket, queue and region settings.

8. What happens when an app accesses S3?

1. AWS SDK looks for credentials
↓ injected container credential endpoint and projected token
2. SDK contacts Pod Identity Agent
169.254.170.23:80
↓ agent uses worker node IAM credentials and pod token
3. EKS Auth validates association and gets app IAM credentials
↓ temporary access key + secret + session token + expiry
4. SDK signs AWS request and refreshes credentials as needed

Application code does not manually perform STS calls. A compromised pod could still misuse temporary credentials until they expire or are revoked/denied, so isolation matters.

9. Validate and troubleshoot

kubectl -n orders get sa orders-api
kubectl -n orders get deploy orders-api -o jsonpath='{.spec.template.spec.serviceAccountName}'
kubectl -n orders exec deploy/orders-api -- printenv | grep '^AWS_CONTAINER_'
# Approved debug pod with the SAME service account and AWS CLI:
aws sts get-caller-identity

Expected assumed role: orders-api-pod-role. Verify a permitted S3 request succeeds; an unauthorized bucket or operation must return AccessDenied. Never print credential token contents. Use CloudTrail and application logs for additional validation.

No injected credentials variables?Check service account, namespace, EKS association, pod restart, compatible EKS version and agent health.
Credentials request times out?Check EKS Auth endpoint, agent local endpoint, node IAM policy, NetworkPolicies and proxy settings.
SDK uses the node role or static keys?Remove explicit credentials and profile settings, validate SDK default chain, and disable metadata fallback.

10. Production security checklist

  • Separate, least-privilege application IAM role per workload/environment.
  • Constrain role trust to cluster ARN, namespace and service-account tags.
  • Restrict iam:PassRole and EKS association lifecycle permissions.
  • Restrict Kubernetes service-account impersonation and pod creation using RBAC and admission policy.
  • Enforce IMDSv2; consider hop limit 1; reduce node role S3/SQS permissions after dependencies migrate.
  • Protect EKS Auth networking and Pod Identity Agent reachability.
  • Enable CloudTrail monitoring; define emergency session revocation/deny procedures.

11. Migration and safe rollback

  1. Inventory app AWS permissions, SDK versions and all old secret consumers. Revoke known-compromised keys immediately.
  2. Install and verify agent in a non-production cluster.
  3. Create pilot application's IAM role, SA and association.
  4. Deploy app using SDK default credentials; test allowed and denied AWS calls and automatic refresh.
  5. Remove obsolete access keys and IAM users once all consumers are cut over.
  6. Roll out through environments using reviewed Terraform and GitOps.

Rollback: pause app rollout or revert to a last secure image, correct IAM/SDK/association issues and test again. Do not restore compromised long-lived credentials.
